Module Development Guide

写一个模块，
只要一个目录

宿主不限制你用什么框架、什么构建工具。它只认两件事：一份 manifest.json，和一个导出 mount(el, api) 的 ES 模块。

AI AGENT 版：给自动化 Agent 的单文件说明在 /docs/agent.md（text/markdown），内容覆盖包结构、manifest 全字段、sidecar、路由、限额、验收与常见错误，可直接抓取。

01职责边界

宿主负责最薄的一层：HTTP 路由、模块发现与安装状态、前端资源挂载、模块选择界面。其余一切——界面、数据、业务逻辑——都在模块里。

运行形态（必须先读）：宿主是运行在 Docker Linux 容器里的 Go 服务（默认 docker compose up -d），模块前端在用户浏览器中执行。容器内不能启动/停止 Windows 进程，不能访问 Windows 命名管道，也读不到用户的 %APPDATA% 等本机目录。需要本机能力时，只能使用浏览器 API（如 File System Access），或由用户在宿主机另行运行受信任的本地服务；宿主不负责拉起宿主机进程。
  • 宿主 不打包模块的依赖，也不参与模块的构建。
  • 模块 不直接读写宿主的文件系统或数据库，只能通过注入的 api 调用宿主能力。
  • 模块之间默认互相隔离，命名空间按 id 划分。

02模块结构

在仓库的 modules/ 下新建一个目录，目录名随意，模块身份由 manifest 里的 id 决定。

modules/hello/
├── manifest.json        # 模块身份证
└── frontend/
    ├── index.js         # 入口，必须导出 mount(el, api)
    └── card.js          # 可选，首页卡片导出 renderCard(el, api)

目录挂载进容器后，刷新页面即可被发现，不需要重启宿主。

注意：id 必须小写字母开头，只含小写字母、数字和短横线，最长 32 字符；同一 ID 出现两次时只保留第一个。

03manifest 字段

{
  "id": "hello",
  "name": "Hello 模块",
  "version": "1.0.0",
  "description": "一句话说明",
  "author": "Mica Home",
  "category": "核心",
  "icon": "spark",
  "tone": "tone-a",
  "permissions": [],
  "frontend": { "entry": "index.js", "card": "card.js" }
}
字段必填说明
id是模块唯一标识，同时是 API 命名空间
name是展示名
version是语义化版本，用于缓存刷新与后续升级
description否卡片描述
author否作者或团队
category否仓库页筛选项，缺省为“未分类”
icon否内置图标名：spark / box / shield / radar / flow / chart / scan / clock / bus
tone否配色倾向：tone-a / tone-b / tone-c / tone-d
permissions否声明的能力清单，当前仅展示，运行时拦截在 P2
frontend.entry是相对 frontend/ 的入口文件，导出 mount
frontend.card否首页卡片入口，导出 renderCard；缺省用 manifest 默认卡片
backend否P0 预留：{ "type": "wasm", "entry": "plugin.wasm" }，尚未执行

04前端契约

入口是标准 ES 模块，宿主用动态 import() 加载后调用 mount。返回的函数会在模块被关闭时执行，用来清理定时器、事件监听等。

export function mount(el, api) {
  el.innerHTML = '<p>Hello</p>';

  return () => {
    el.innerHTML = '';
  };
}

注入的 api

成员说明
api.id / api.version当前模块标识与版本
api.request(path, init?)请求本模块命名空间，自动拼成 /api/m/<id>+path，返回已解析的 JSON
api.toast(text)宿主统一样式的轻提示
api.close()关闭当前模块面板
建议：模块内部样式使用自己的类名前缀（如 .mh-notes），并把样式注入到 document.head 一次即可，避免与宿主或其他模块冲突。

卡片契约（可选）

声明 frontend.card 后，首页只渲染「已启用」模块，并把卡片内容区交给模块绘制。宿主负责卡片外壳（图标、名称、版本、底栏、悬停与网格），模块只填内容区，且只能改自己的 DOM。

export function renderCard(el, api) {
  el.innerHTML = `
    <div class="mh-todo-status">3 条待办</div>
    <button type="button" data-no-open>快速新建</button>`;

  function onQuickAdd() { api.toast('待办已新建'); }
  el.addEventListener('click', onQuickAdd);
  api.toast('卡片已就绪');

  return () => {
    el.removeEventListener('click', onQuickAdd);
  };
}
卡片 api说明
api.id / api.version当前模块标识与版本
api.open()打开本模块面板，等同点「打开」
api.toast(text)宿主统一轻提示
api.request(path, init?)请求本模块命名空间
约束：卡片渲染限时 1.5 秒，抛错或超时会自动回退成 manifest 默认卡片；不要在卡片里调用 api.close()；卡片内的按钮需要带 data-no-open 或使用 button/a/input 等原生标签，避免误触打开面板。

上传安装模块包

# 命令行安装

06本地开发

宿主以容器运行，模块目录是挂载进去的，所以改完模块文件只要刷新浏览器即可，不用重建镜像。

# 启动（首次会构建镜像）
docker compose up -d --build

# 看宿主日志，确认模块扫描结果与请求
docker logs -f mica-home

# 新增模块后无需重启
# 在 modules/ 下新建目录，写上 manifest.json 与 frontend/index.js，刷新页面

模块前端资源响应的 Cache-Control 是 no-cache，并附带版本查询参数，修改后会立即生效。

07能力边界

当前版本（P0）已经打通：发现 → 安装 → 加载 → 挂载 → 卸载。以下能力尚未实现，写模块时请勿依赖：

  • 在线安装：可从「模块管理」上传 zip；尚无 OCI 仓库远程拉取与在线版本更新。
  • 签名校验：卡片上的安装状态不代表来源可信。
  • 权限拦截：permissions 只做展示，不会阻止任何调用。
  • 后端运行时：WASM 后端与 PostgreSQL 存储仍在计划中。
  • 本机进程 / 文件 / 命名管道：宿主在 Linux 容器内，既不能拉起 Windows 进程，也不能访问命名管道或用户目录；需要容器内常驻进程的模块按第 9 节 Sidecar 契约实现（宿主侧待开发）。

08交付与验收

写模块前先读本页；涉及颜色、圆角与主题跟随，必须同时读 主题设计指南。下面这些约束文档其他章节没有逐条列出，但会直接决定模块能不能装、能不能跑。

必须满足

  • 包结构：zip 根目录直接是 manifest.json 与 frontend/，不能多套一层文件夹；解压后的目录名就是 <id>。
  • 同 ID 拒绝覆盖：已存在同 id 时安装返回 409。要重复测试，先在「模块管理」卸载（删除目录）再重新上传。
  • 停用不等于删除：停用只取消启用状态，模块目录保留；卸载才会删除 modules/<id> 目录。
  • P0 没有后端与数据库：backend、permissions 只是声明，不会执行；数据只能放 localStorage 或模块自带的静态文件。
  • 纯 ESM：入口与相对导入的文件都必须是浏览器可直接加载的 ES 模块，不依赖构建步骤与 Node 运行时。
  • 样式隔离：类名统一 .mh-<id> 前缀，<style> 只注入一次，不改写 :root 或 body；颜色与圆角只用 --mh-* 令牌。
  • 图标名：icon 只能取内置值 spark / box / shield / radar / flow / chart / scan / clock / bus。
  • 入口契约：必须导出 mount(el, api)，并返回清理函数；宿主关闭面板时会调用它。
  • 卡片契约：若声明 frontend.card，必须导出 renderCard(el, api)，限时 1.5 秒；只填卡片内容区，不接管外壳。

验收步骤

  • 打包 zip → 「模块管理」上传 → 列表出现该模块且状态为 ENABLED。
  • 首页出现卡片；自定义卡片内容正常渲染，未声明 card 时显示默认描述。
  • 点开卡片，模块面板正常挂载；关闭后重新打开不残留旧内容。
  • 刷新页面后模块仍可用；浏览器控制台无报错。
  • 浅色与深色各看一遍：文字可读、无白色块、按钮与边框正常。
  • 在模块管理中停用 → 首页卡片消失、面板资源不可访问；再启用 → 卡片恢复。
AI 生成模块时：把本页与「主题设计指南」两页一起给它，并要求它按上面的验收步骤自测，而不是只输出代码。

09Sidecar 契约

需要容器内常驻进程的模块（如 mihomo）通过 sidecar 提供能力。分三层：宿主只管理 mihomo-watch，watch 管理内核，模块前端只通过反代调用 watch。

名词含义
Mica Home / 宿主容器内的 Go 主进程（PID 1）
sidecar一种机制/角色：模块附带的常驻程序，不是某个固定程序
mihomo-watch本模块的 sidecar 程序，由模块包提供
sidecar supervisor宿主进程内部的管理代码，不是独立程序
mihomo被 watch 管理的内核，不是 sidecar
 
模块前端 --/api/m/<id>/*--> 宿主 --启动/停止--> mihomo-watch --管理--> mihomo
完整契约：宿主仓库的 docs/SIDECAR-CONTRACT.md。下面是最小实现要点，模块方按完整契约实现。

9.1 包结构与目录

manifest.json
frontend/
sidecar/
  mihomo-watch        # 宿主执行的入口
  mihomo              # 由 watch 拉起，宿主不直接执行

安装后：frontend/ → modules/<id>/；sidecar/ → /data/sidecar/<id>/；用户数据放 /data/modules/<id>/；日志在 /data/logs/<id>.log。sidecar 文件不得进入模块目录。

9.2 manifest 声明

"sidecar": {
  "binary": "sidecar/mihomo-watch",
  "executables": ["sidecar/mihomo-watch", "sidecar/mihomo"],
  "platform": "linux/amd64",
  "sha256": {
    "sidecar/mihomo-watch": "<64 位 hex>",
    "sidecar/mihomo": "<64 位 hex>"
  },
  "args": [],
  "env": {},
  "healthPath": "/health",
  "healthTimeoutSec": 5,
  "socketName": "mihomo-watch.sock",
  "permissions": ["process.run", "fs.write:/data/modules/mihomo"]
}
  • 不再声明 ports、autoStart、stopOnDisable：启用即启动、停用即停止，内核端口由 watch 管理。
  • 首版只接受 linux/amd64；纯 Go 建议静态编译（CGO_ENABLED=0）。
  • 宿主校验平台与 SHA256，并给 executables 加可执行位。
  • healthTimeoutSec 可选，默认 5 秒，范围 1–120；Python / JVM 等启动慢的 sidecar 可调大，超时只标记 degraded，不会杀进程。
  • 运行层是 Debian slim（glibc），可运行 Python 与带 C 扩展的依赖；纯 Go 静态二进制同样适用。

9.3 两条通道

通道调用方鉴权用途
healthPath（默认 /health）仅宿主X-Mica-Tokenhealth 检查
/api/m/{id}/* → /*模块前端（经宿主反代）X-Mica-Token配置、订阅、节点、内核控制
  • /__host/* 保留给后续双 token 管理通道，宿主反代当前直接拒绝。
  • 宿主保留 info、ui、__status、__logs，watch 的业务路径不要使用这些前缀。
  • watch 只监听 127.0.0.1 或 Unix socket，不得监听 0.0.0.0。

9.4 watch 必须实现

方法路径说明
GEThealthPath（默认 /health）watch 存活，返回 ok 与版本；带 X-Mica-Token
GET/status模块通道：内核是否运行、PID、版本、实际端口
任意模块业务路径由 watch 自行定义，可代理 mihomo 控制 API

宿主注入 MICA_DATA_DIR、MICA_MODULE_ID、MICA_MODULE_DIR、MICA_MODULE_DATA_DIR、MICA_SIDECAR_DIR、MICA_SIDECAR_ADDR、MICA_SIDECAR_TOKEN、MICA_HOST_TOKEN；args 支持 ${MICA_*} 占位符。

9.5 生命周期

事件宿主watch
启用启动 watch，等 /__host/health（≤5s）启动 mihomo，准备控制口
停用SIGTERM，10s 后杀进程组停止 mihomo，清理子进程
卸载停 watch，删 /data/sidecar/<id>，保留用户数据退出前清理内核
watch 崩溃退避重启，最多 5 次；稳定 60s 重置启动时清理残留内核
mihomo 崩溃不介入自行重启

9.6 数据面

内核代理端口（如 7890）只在容器内 127.0.0.1 监听，不通过 docker-compose 发布，宿主机和局域网都不可见。浏览器模块不能把它当 HTTP 代理使用，只能通过反代做控制；容器内其他进程可以直连。

9.7 安装、升级与限额

  • 前端包 20MB、sidecar 包 512MB、单次上传 256MB、文件数 30000。
  • 同 ID 版本不同允许升级：停旧 → 备份 → 替换 → 启动 → 失败回滚；同版本重装拒绝。
  • 安装页展示二进制、平台、哈希、体积与权限；启用时确认一次，升级后重新确认。
  • 宿主只执行声明过的二进制，参数数组直传，不经过 shell，不传递宿主机密钥。

9.8 验收要点

  • 启用后 healthTimeoutSec（默认 5 秒）内 /api/m/{id}/__status 为 running，模块通道 /status 显示内核运行。
  • 停用后 watch 与内核两个进程都消失；卸载后 /data/sidecar/<id> 被删除。
  • kill watch 或 kill 内核后能自动恢复；宿主重启后已启用模块恢复。
  • docker port mica-home 看不到 7890；宿主机访问 7890 失败。
  • 未启用模块、/__host/*、无 token 的请求分别返回 403/403/401。
  • 平台或 SHA256 不匹配拒绝安装；升级失败能回滚。

10宿主侧实现

首版已完成：流式上传与双目标安装、平台/SHA256 校验、sidecar 启停、崩溃退避重启、同 ID 版本升级与回滚、权限确认、日志轮转、可配置健康检查、__status/__logs 与 /api/m/{id}/* 反代（含 WebSocket）。双 token 管理通道与 service/shared sidecar 仍不在首版范围。

10.1 代码结构

internal/module/module.go        # manifest.sidecar 解析、安装、升级、卸载
internal/sidecar/manager.go      # 生命周期、状态机、日志、退避重启、反代客户端
internal/sidecar/proc_linux.go   # exec、进程组、SIGTERM/SIGKILL、僵尸回收
internal/host/host.go            # 安装/启用/确认/卸载与 /api/m/{id}/* 路由

10.2 安装

  • 上传上限 256MB；multipart 流式写入 /data/tmp，不再整包读入内存。
  • 打开 zip 后分类：frontend/ 与 manifest.json 归模块包；sidecar/ 归 sidecar 包；分别限额 20MB / 512MB，单文件 512MB，文件数 30000。
  • 校验 platform、每个文件的 sha256，给 executables 加 0755。
  • 事务化：先解到临时目录，全部通过后再落盘；同版本重装 409，版本不同进入升级。
  • 升级：停旧 watch → 备份旧模块与 sidecar → 替换 → 重新扫描 → 失败自动回滚旧版本。
  • 安装后不自动启用：sidecar 声明了 permissions 时先确认，再由用户启用；无权限声明则直接启用。
  • 安装时创建 /data/modules/<id>；sidecar 文件只进 /data/sidecar/<id>。
  • 安装页展示上传/解压上限与数据盘剩余空间；解压峰值约为 zip + 解压总和的 2 倍，大包前先确认磁盘余量。

10.3 运行时

环节实现
启动exec.Command 直传 args（无 shell），注入 env，工作目录 /data/modules/<id>，stdout/stderr 写日志
进程组Setpgid + Pdeathsig；停用时先 SIGTERM，12 秒后 SIGKILL 整个进程组
就绪轮询 manifest 的 healthPath（默认 /health），超时为 healthTimeoutSec（默认 5 秒）；失败标记 degraded
崩溃1/2/5/10/10 秒退避重启，最多 5 次；稳定运行 60 秒后重置计数，之后标记 degraded 并停止重启
日志/data/logs/<id>.log，超过 5MB 滚动为 .1/.2
宿主退出先停 HTTP，再停全部 watch；容器退出不依赖子进程自行退出
宿主重启扫描已启用且已确认的模块，自动拉起 watch
孤儿清理停用杀整个进程组；watch 崩溃后回收被 init 收养的僵尸子进程

10.4 反代

  • 使用标准库 httputil.ReverseProxy：保留方法、查询、请求体、状态码、响应头与 Range。
  • 支持 WebSocket / HTTP Upgrade 与流式响应（FlushInterval = -1），可用于实时日志与任务进度；模块前端不需要为实时推送改轮询。
  • 优先 /data/run/<socketName> 的 Unix socket；不支持时分配回环端口并注入 MICA_SIDECAR_ADDR。
  • 注入 X-Mica-Token 并覆盖客户端自带值；拒绝 /__host/*；未启用模块 403，token 不匹配 401。
  • 管理通道首版复用 X-Mica-Token，由宿主内部直接调用 healthPath；反代仍拒绝 /__host/*，双 token 待补。

POST /api/modules/<id>/confirm     // 记录 id + 指纹，升级或改权限后需重新确认

10.6 权限与审计

  • 安装响应返回 sidecar 的平台、SHA256 与权限；管理页启用时弹窗展示权限，确认后记录 id + 指纹（版本、哈希或权限变化即失效）。
  • 宿主只执行 manifest 声明的 binary，参数数组直传，不经过 shell，不传递宿主机密钥。
  • 生命周期与代理访问写审计日志；越界请求返回 403/401 并记录。
  • 宿主能限制“执行哪个文件、给哪些环境变量、反代哪些请求”，但无法在 OS 层完全限制原生进程读写 /data；sidecar 仍应视为受信任代码。

10.7 实施顺序

  1. 假 sidecar：提供 /health、模块 /status，用于联调。
  2. 安装器：流式上传、双目标解压、限额、平台/哈希、事务落盘。已完成
  3. supervisor：启停、进程组、日志轮转、退避重启、宿主重启恢复。已完成
  4. 反代：Unix/TCP、token、403/401、状态与日志接口、WebSocket 升级。已完成
  5. UI：安装展示、权限确认、管理页 sidecar 状态。已完成
  6. 升级与回滚：停旧 → 备份 → 替换 → 启动 → 失败回滚。已完成
  7. 接真实 mihomo：替换假 sidecar，只做联调。已完成（2.0.1 → 2.0.3 实测）

10.8 首版边界

  • 只支持 linux/amd64、managed 模式；不做 service / shared sidecar。
  • 一个模块最多一个 sidecar；不做签名校验，只做 SHA256。
  • 日志只提供 tail，不做 SSE 流；7890 等业务端口不发布。
  • 反代已支持 WebSocket 与流式响应，模块可直接使用原生实时接口。
  • 管理请求仍复用 X-Mica-Token，/__host/* 双 token 通道留待后续。
  • mihomo 的进程、配置、订阅全部由 watch 负责，宿主不实现任何 mihomo 逻辑。
